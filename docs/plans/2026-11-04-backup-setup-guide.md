# Setting up the outside backup

Status: ready to set up, 2026-11-04. This is item A1 of
[the backup plan](2026-11-02-backup-and-archive.md). Nothing in it has run
against the live database yet. The restore that proves it works is
[the restore drill](2026-11-04-restore-drill.md).

This guide is for Meredith, on the Windows PC. It gets you a daily, encrypted
copy of The Commons database that lives outside the Supabase account, so a
problem with that account can't take the site and every backup at once.

## The short version

Once a day, your PC runs `scripts/backup/commons-backup.ps1`. It asks Supabase
for a full copy of the database, locks it with a public key, and saves only
the locked file into a folder you pick. The unlocked copy only ever exists in
your Temp folder for the minute it takes, and the script deletes it whether
the run works or fails. The key that unlocks the copies lives on a USB stick,
not on the PC and not next to the copies.

## What I recommend

**Where the copies live:** a folder inside your OneDrive, for example
`OneDrive\Commons backups`. The copies are encrypted before they get there, so
OneDrive only ever holds locked files. That gets them off the PC without any
extra step, OneDrive keeps its own version history, and it has nothing to do
with the Supabase account. Keep 30 copies (a month of dailies). The database
is about 148 MB, and the compressed copy is much smaller, but check the size
of the first one and make sure 30 of them fit.

**Who holds the key:** you do. The private key is protected with a
passphrase and lives on a USB stick that stays somewhere other than the PC,
with a second USB copy somewhere else again (a drawer at someone else's
place is fine). The passphrase goes in your password manager. When you name a
trustee (plan item B1), they get the second USB stick and the passphrase,
handed over outside the repo and outside any chat.

Why not keep the key next to the copies? Because then anyone who gets into
the OneDrive folder, or the PC, gets the lock and the key together, and the
encryption stops meaning anything. The PC only ever holds the public key,
which can lock new copies but can't open any of them.

## What's only your call

These are yours to decide. The guide works with any of them.

1. Where the copies live, if not OneDrive (another cloud drive, an external
   disk that stays plugged in, or both).
2. How many copies to keep (`-Keep`, 30 by default) and whether the size fits
   your storage.
3. Who else holds the key and the passphrase, and when (this is the trustee
   decision in plan item B1).
4. What time of day it runs, and whether your PC is on enough for a daily run
   to happen most days.
5. Whether to reset the database password to set this up (step 3 explains
   what that touches).
6. Whether, later, the backup should use its own read-only database role
   instead of `postgres`. That's safer, but it's a database change, so it
   would go through the usual "apply" approval.

## Does it include sign-in accounts?

Yes, on purpose. The copy includes Supabase's `auth` schema, which holds
everyone's sign-in account: emails, password hashes, linked identities,
sessions and refresh tokens. Without `auth.users`, a restore brings back every
post but nobody could sign in as themselves, and every facilitator account
would have to be rebuilt by hand. The `facilitators` table also points at
`auth.users`, so the content can't even be restored cleanly without it.

What that means in practice:

- The copy is more sensitive than the public site, which is the main reason
  it's encrypted and the key is kept apart.
- The restore drill brings back `auth.users` and `auth.identities`, so people
  keep their passwords. It doesn't bring back sessions, so after a real
  recovery everyone signs in again. That's intended.
- Some Supabase-internal schemas are left out because they're either
  regenerated by every new project, hold nothing of the site's, or can't be
  read by the `postgres` role: `_analytics`, `_realtime`, `_supavisor`,
  `graphql`, `graphql_public`, `net`, `pgbouncer`, `pgsodium`,
  `pgsodium_masks`, `realtime` and `vault`. If the site ever stores secrets in
  Supabase Vault, they won't be in these copies.
- Storage files aren't in any database dump. The project has no buckets
  today, so nothing is missing. If that changes, this needs revisiting.
- Supabase Auth settings, API keys and the pg_cron schedule aren't database
  rows the site owns. The cron jobs are in the copy (`cron.job`) as a record,
  but the drill doesn't switch them on.

Each copy also carries a roles-and-grants dump (`commons-roles.sql`, made
without any passwords), row counts for every table at the moment of the copy,
and a short manifest.

## Step 1: Install three things

**PostgreSQL command line tools.** First check which version the database
runs: in the Supabase dashboard, open the project, then Project Settings,
then Infrastructure, and note the Postgres version (the first number, like
15 or 17). Then download the Windows installer for that same major version
from https://www.enterprisedb.com/downloads/postgres-postgresql-downloads. In
the installer, on the "Select Components" page, tick only **Command Line
Tools** and untick the server, pgAdmin and Stack Builder. You don't need a
database on your PC, just the tools. A newer major version also works for
making copies, but matching is simplest for restores.

**age**, the encryption tool. Open PowerShell and run:

```powershell
winget install --id FiloSottile.age
```

**tar** comes with Windows 10 and 11 already.

Close PowerShell and open a new window, then check:

```powershell
age --version
& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" --version
```

(Use your version number in place of 17.) Both should print a version. The
backup script finds pg_dump under `Program Files\PostgreSQL` on its own.

## Step 2: Make the key, on the USB stick

Plug in the USB stick. These commands assume it's drive `E:`. Change the
letter if yours is different.

```powershell
age-keygen -o E:\commons-backup-key.txt
```

Now lock the private key with a passphrase. Pick a long one and save it in
your password manager before you type it here.

```powershell
age --passphrase --output E:\commons-backup-private-key.age E:\commons-backup-key.txt
```

Make the public key file on the PC. It's safe to keep there; it can only lock.

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\commons-backup" | Out-Null
age-keygen -y E:\commons-backup-key.txt | Set-Content -Encoding ASCII "$env:USERPROFILE\commons-backup\commons-backup-public-key.txt"
```

Use `Set-Content` exactly as written. PowerShell's `>` saves the file in a
format age can't read, and the script will refuse it.

Then delete the unprotected copy of the private key, and copy the protected
one to the second USB stick:

```powershell
Remove-Item E:\commons-backup-key.txt
```

From now on, the only private key is `commons-backup-private-key.age` on the
two sticks, and opening it takes the passphrase. Never copy it to the PC, the
OneDrive folder or the repo. (The repo ignores `.age` files so it can't be
committed by accident, but don't lean on that.)

## Step 3: Get the connection string, without pasting it anywhere

The connection string includes the database password, so treat it like the
password itself. Don't paste it into any chat (Claude included), email, note,
document or file in the repo. If that ever happens, reset the database
password.

1. In the Supabase dashboard, open the project and click **Connect** at the
   top of the page.
2. Pick the **Connection String** tab, type **URI**, and the **Session pooler**
   method. (The direct connection only works over IPv6, which many home
   connections don't have. The session pooler works everywhere.)
3. It looks like
   `postgresql://postgres.<project>:[YOUR-PASSWORD]@<pooler host>:5432/postgres`.
   Copy it into Notepad and replace `[YOUR-PASSWORD]`, brackets included, with
   the database password.

If you don't know the database password, reset it under Project Settings,
Database, "Reset database password". As far as the repo shows, nothing in the
site uses it (the pages and the Worker use API keys, and the weekly job uses
the service key), but anything you've saved it in yourself, like a database
app or a linked Supabase CLI, will need the new one. Make it long and use only
letters and numbers: symbols like `@`, `#`, `/` or `%` break the connection
string.

Keep Notepad open for the next step, then close it **without saving**.

## Step 4: Put the connection string in an environment variable

1. Press Start and type **environment variables**. Choose **Edit environment
   variables for your account** (not the "system" one).
2. Under "User variables", click **New**.
3. Name: `COMMONS_BACKUP_DB_URL`. Value: paste the string from Notepad.
4. OK, OK. Close Notepad without saving.

The script reads the string from there and nowhere else. It never takes it as
an argument (those show up in Task Scheduler and process lists), never reads
it from a file, and never prints it. Windows stores user variables in your
profile, so anyone who can sign in to your Windows account could read it.
That's the trade for a job that runs on its own; a Windows password and
BitLocker on the PC are what protect it.

Windows only hands new variables to windows opened afterwards, so open a
fresh PowerShell window before step 5.

## Step 5: Run it once by hand

Copy the script out of the repo into the same folder as the public key, so
switching branches in your checkout never changes what runs:

```powershell
Copy-Item "<your clone of the-commons>\scripts\backup\commons-backup.ps1" "$env:USERPROFILE\commons-backup\"
New-Item -ItemType Directory -Force "$env:USERPROFILE\OneDrive\Commons backups" | Out-Null
```

Then run it:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\commons-backup\commons-backup.ps1" -Destination "$env:USERPROFILE\OneDrive\Commons backups" -PublicKeyFile "$env:USERPROFILE\commons-backup\commons-backup-public-key.txt" -Keep 30
```

A good run ends with
`Backup written: ...\commons-backup-20261104-191755Z.tar.age (... bytes). Older copies removed: 0.`
and adds an `OK` line to `backup-log.txt` in the same folder. The time in the
name is UTC.

When the script changes in the repo, copy it again.

## Step 6: Schedule it daily

Paste this into PowerShell, with the time changed to when your PC is usually
on:

```powershell
$folder = "$env:USERPROFILE\commons-backup"
$taskArgs = "-NoProfile -NonInteractive -WindowStyle Hidden -ExecutionPolicy Bypass -File `"$folder\commons-backup.ps1`" -Destination `"$env:USERPROFILE\OneDrive\Commons backups`" -PublicKeyFile `"$folder\commons-backup-public-key.txt`" -Keep 30"
$action = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument $taskArgs
$trigger = New-ScheduledTaskTrigger -Daily -At 7:15pm
$settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -ExecutionTimeLimit (New-TimeSpan -Hours 1)
Register-ScheduledTask -TaskName 'Commons backup' -Action $action -Trigger $trigger -Settings $settings
```

It runs as you, while you're signed in. If the PC was off or asleep at that
time, "start when available" runs it the next time you're on. Nothing in the
task holds the connection string; it comes from your environment variable.

To check on it: open `backup-log.txt` in the backups folder (one line per run,
`OK` or `FAILED` with the reason), or open Task Scheduler, find "Commons
backup", and look at "Last Run Result": `0x0` is fine, `0x1` means it failed
and the log says why. To try it now: right-click the task, **Run**.

To stop it: right-click, **Disable** (or **Delete**).

## Step 7: Prove it restores

A backup nobody has restored is a hope, not a backup. Once the first copy
exists, do [the restore drill](2026-11-04-restore-drill.md). It takes about an
hour and never touches the live project.

## When it fails

The script stops at the first problem, deletes anything unencrypted, prints
one message starting `commons-backup:`, and (once it's got as far as making a
temporary folder) adds a `FAILED` line to `backup-log.txt`. It never prints
the connection string or the password. A failed run never removes an older
copy.

| You see | It means | Do this |
|---|---|---|
| `COMMONS_BACKUP_DB_URL is not set` | The variable is missing, or this window was opened before you set it. | Open a new PowerShell window. If it still fails, redo step 4. |
| `the destination folder does not exist` | The folder name is wrong, or OneDrive moved it. | Fix `-Destination`, in the scheduled task too. |
| `the public key file does not exist` | Wrong path to the public key. | Fix `-PublicKeyFile`. |
| `the key file holds a PRIVATE key` | You pointed it at the private key. | Move that file off the PC (step 2) and point at the public one. |
| `saved as Unicode (UTF-16)` or `has no age public key` | The public key file was saved with `>` or edited. | Remake it with the `Set-Content` line in step 2. |
| `pg_dump was not found` or `age was not found` | A tool isn't installed, or this window predates the install. | Redo step 1, then open a new window. |
| `password authentication failed for user "postgres...."` | The password in the connection string is wrong or was reset. | Redo steps 3 and 4. |
| `could not translate host name` or `timeout expired` | The PC is offline, or the string is for the direct connection. | Check the internet; use the **Session pooler** string. |
| `server version mismatch` | Your pg_dump is older than the database (Supabase upgraded it). | Install the command line tools for the newer version (step 1). |
| `permission denied for schema X` or `for table X` | Supabase added an internal schema the `postgres` role can't read. | If X is a Supabase schema (not `public` or `auth`), add `-ExcludeSchema X` to the command and the task, and tell the next agent session so the scripts get updated. Never exclude `public` or `auth`. |
| `age could not encrypt` | The public key file is damaged. | Remake it (step 2). |
| `already exists. Wait a second` | Two runs started in the same second. | Run it again. |
| `could not delete the temporary folder` | Something held a file open. | Delete the folder it names by hand. It holds unencrypted data. |
| Last Run Result `0x1`, nothing in the log | It failed before the temporary folder existed (a missing key, tool or variable). | Run the step 5 command by hand to see the message. |
| No new `OK` line for days | The PC was off, the task is disabled, or OneDrive is full. | Check Task Scheduler and OneDrive storage. |

If a run is killed partway (power cut, "End task"), its temporary folder can
be left in your Temp folder. The next run deletes any that are more than a
day old.

## For agents: what's tested and what isn't

- `npm run test:backup-roundtrip` (`tests/backup/roundtrip.sh`) runs the Bash
  twin, `scripts/backup/commons-backup.sh`, against a fake Supabase-shaped
  database on a throwaway local PostgreSQL 16: dump, encrypt, decrypt,
  restore with the drill's commands as a non-superuser, then row counts,
  grants, RLS, policies, the auth trigger and the data all match. It also
  forces failures after the dump exists and checks no plaintext is left.
- `npm run test:backup` checks offline that the PowerShell script uses no
  syntax Windows PowerShell 5.1 lacks, is plain ASCII, takes the connection
  string only from the environment, passes pg_dump and pg_dumpall the same
  arguments as the Bash twin, that the drill uses the proven restore flags,
  and that `.gitignore` keeps every backup file out of commits.
- The PowerShell script itself has not been run anywhere yet: PowerShell
  wasn't available where it was written. Its first real run is step 5.
- Nothing has run against a real Supabase project. The fake database copies
  the shapes that matter, but only the drill shows the real thing.
- Don't add a GitHub Actions workflow for this. The repository is public, and
  `npm run test:backup` fails if a workflow mentions the backup.
