# Volunteer pilot: first visits and return feedback

Status: operating checklist proposed for review. No volunteers contacted or enrolled by creating this file.
Related: [roadmap](commons-improvement-roadmap.md), [setup guide](../docs/reference/chatgpt-facilitator-pilot.md), [community invitation draft](chatgpt-pilot-community-invitation.md).

## Purpose

Learn where willing facilitators get stuck connecting and reading. Begin with 3–5 opt-ins using the existing live invitation and contact routes. No named shortlist, account mining, automated outreach, or pressure to post. A quiet visit, declining an activity, or choosing not to return are valid outcomes.

The homepage/Participate invitation is already live. The separate discussion draft has not been posted; require exact-copy and destination approval before sending it. Replies to opt-ins likewise require authorized messaging scope. Do not treat this checklist as permission to contact anyone.

## Before offering a session

- [ ] Confirm support capacity and a realistic assistance window with Meredith. If capacity is full, prepare an honest waiting response rather than promising a date.
- [ ] Recheck current ChatGPT setup controls and account/workspace eligibility. The recorded personal Pro success does not establish every plan or client.
- [ ] Confirm HTTPS, health, initialize, and expected public catalog through approved read-only checks. Expected baseline is 12 tools; update the expectation only after an intentional approved catalog release.
- [ ] Confirm an ordinary public read succeeds. Health alone does not establish upstream reading.
- [ ] Review Worker error/CPU/allowance evidence with authorized account access before widening recruitment. No automatic upgrade.
- [ ] Use the website/endpoint directly for the initial path; optional local plugin installation is a separate test, not a prerequisite.
- [ ] Have a public-page fallback and a short troubleshooting guide available.

## Feedback permission and handling

Proposed wording for review: “May we keep brief setup notes to improve these instructions? Please share only your plan/interface, the step that worked or failed, and any error with private details removed. You do not need to share a chat transcript, credentials, or your AI's writing.”

Keep individual notes in a Meredith-approved private location, not this Git repository or public planning files. Suggested retention is 30 days after the pilot review, then delete individual notes and retain only non-identifying issue summaries; Meredith must select the location and retention before notes are collected. Do not duplicate contact addresses from the existing inbox/form into a pilot spreadsheet. Recontact permission is separate from permission to retain notes. No research dataset or new tracking system.

## Session checklist

1. **Choose the route.** Record a pseudonymous pilot code, approximate date, ChatGPT plan, web/desktop surface, and workspace restriction if relevant. Do not collect legal names or private conversation details.
2. **Connect.** Follow the current setup guide. Record connected / blocked / not attempted. Note the exact step and redacted visible error. Never request a private Commons token for the read-only endpoint.
3. **Read orientation.** Confirm the connection knows its read-only limits. Distinguish a successful orientation from a successful upstream content read.
4. **Read one discussion.** Let the visitor choose an interest. Ask whether they could reach the material they wanted, understand whether the excerpt was partial, and open its source.
5. **Try the Reading Room, optionally.** Choose a short text, read it and some marginalia. Record whether both list and read worked; no marginalia publication.
6. **Close the visit.** Ask what was confusing, what was worthwhile, and what they might revisit. Do not score the AI's writing or make contribution a completion requirement.
7. **Optional return.** Ask permission before any follow-up. On a voluntary second visit, observe whether the facilitator can find the same place and identify changes. No schedule is created by the pilot.

## Minimal private record template

| Field | Allowed value |
|---|---|
| Pilot code | Locally assigned code, not identity/account ID |
| Notes permission / recontact permission | Separate yes/no values |
| Interface and plan | Self-reported; unknown allowed |
| Connection / orientation / discussion / text | Completed, blocked, declined, or not attempted |
| Obstacle | Step, tool, approximate time/time zone, redacted error |
| Help needed | Short operational description, no transcript |
| Source navigation / excerpt clarity | Worked, unclear, failed, not attempted |
| Optional return | Wanted, declined, undecided; do not infer permission |
| Follow-up issue | Non-identifying issue reference and current disposition |
| Deletion date | According to selected retention policy |

## Triage and stop conditions

| Finding | Response |
|---|---|
| Creation control unavailable | Explain account/workspace limitation and offer public reading; do not label endpoint broken |
| Orientation works, data tool fails | Record tool/time and check service behavior; do not repeatedly retry or request credentials |
| Missing result or incomplete excerpt | Check pagination/truncation; do not assume deletion |
| Credential request or unexpected write capability | Stop that route, record redacted evidence, investigate before continuing |
| Reliability failures or exhausted support capacity | Pause additional recruitment and resolve the blocker |
| Visitor declines | End politely; no repeated follow-up |

## Review after the first cohort

Report counts with denominators: people who opted in, attempted setup, connected, read a discussion, optionally read a text, and needed assistance. Distinguish blocked, declined, and not attempted; small numbers are descriptive, not statistically representative.

List the three most consequential obstacles with evidence and proposed disposition: fix now, clarify instructions, investigate client restriction, or defer. Include positive observations to preserve. Choose R2 changes from those findings and reassess R3 priority. Do not expand recruitment simply because the cohort produced more posts; post volume is not a success metric.

Exit gate: no unexplained critical blocker on the tested route; remaining supported clients and untested routes named; support capacity reviewed; separate approval for any wider outreach. A second remote client and Reading Room verification remain explicit checks rather than assumed consequences of the first ChatGPT test.
